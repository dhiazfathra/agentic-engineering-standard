Problem: matches your Tokopedia/Dermalicious depth, but every layer — infra, deploys, auth, storage — is a seam an agent has to get right alone.

Solution: reserve this pattern for when the project needs to justify itself as a scale artifact, not for a fast solo build.

Problem: one framework, one deploy — the deepest module of the four for build simplicity. But the wall is the same 1 GB, this time with a hard lock instead of a pause: exceed it and Blob is unreachable for 30 days.

Solution: good default until real usage; the seam that leaks first is storage, not architecture — you already hit it here.

  • locality: highest — single repo, single deploy target
  • leverage: presigned direct-upload pattern reused for any blob provider later
  • leak: 30-day lockout on overage, no graceful degrade

Next.js + Turso (Vercel) + MinIO (self-hosted blob only)

Strong one seam moved, not multiplied 
flowchart LR
  Ext[Extension] --> Api[Next.js API route]
  Ext -. presigned PUT .-> Minio[MinIO on VPS]
  Api --> Turso[(Turso libSQL)]
  Api -. presign .-> Minio

Problem: the only candidate where the wall moves — storage becomes disk you own instead of a vendor cap. Everything else stays exactly as deep as the pure-Vercel version.

Solution: swap only the blob adapter; DB, API routes, frontend untouched. One new module (MinIO + TLS + CORS), not a rearchitecture.

  • locality: storage concern now fully isolated behind one presign interface
  • leverage: same client-direct-upload shape as Vercel Blob — low switching cost
  • new cost: you now own uptime, TLS, and backups for one VPS
ADR-worthy: presigned-URL contract is the seam — document it once, both blob adapters implement it.

Top pick: Vercel + Turso + self-hosted MinIO

It's the only option where the wall you already hit moves out of the way without adding a second architectural seam. Everything else in the stack stays as deep and as agent-buildable as the pure-Vercel version.
